# G1 执行手册 v0.1

> 日期 2026-11-02 ｜ 定位：从"发帖"到"G1 决策 memo"的操作手册，**不重复**判据表与访谈提纲。
> 口径来源（冲突时以上游为准）：`docs/用户验证包-v0.1.md` §1/§2/§7/§9、`docs/招募帖与问卷-v0.1.md` §2/§3/§5、`docs/G1访谈员手册-v0.1.md`。
> 锁定口径：H1–H4 硬门槛；20 户 = 老人 8 / 儿童 6 / 纯危险设备 6；A/B/C 三档 6/7/7；一线/新一线 ≤12；记录表 13 列。
> **三条边界**：① `var/g1/demo/` 全部是合成数据，**不是用户证据**，不得写进报告与决策；② 脚本不发送任何消息、不替你做同意；③ 本文命令参数以脚本 `--help` 实际输出为准，不预设、不编造。

**环境约定**：Windows + git-bash，仓库根目录执行；统一用 `.venv/Scripts/python.exe`（仓库已带环境）。若用 uv，等价写法为 `uv run python scripts/...`。输入输出路径均相对仓库根。

## 1. 一页总览：7 步流程

### 1.1 流程图

```text
[1 发帖] → [2 导出报名] → [3 筛选] → [4 约访] → [5 访谈/录音] → [5b 转写] → [6 分析] → [7 决策]
  人          人+机          机+人        人            人             机           机+人        人
  必须         必须         脚本+抽查     必须          必须          可选         脚本+复核     必须
```

> 主流程按 **7 步**计：转写（5b）是第 5 步的子步骤，单独成节只为排障方便，不改变 7 步划分。

### 1.2 每一步谁做、要多久、产物是什么

| 步 | 环节 | 谁做 | 输入 | 产物 | 建议耗时 |
|---|---|---|---|---|---|
| 1 | 发帖 | **必须本人**（用你的账号） | 三版文案、报名表单链接 | 投放记录、报名入口 | Day2 两波（10:00 / 19:30） |
| 2 | 导出报名 | 人+机器 | 表单后台 | `var/g1/responses.csv` | 10 分钟/次 |
| 3 | 筛选 | 脚本 + 本人抽查 | `responses.csv` | `screened.csv`、`summary.json` | 15 分钟 |
| 4 | 约访 | **必须本人** | 合格/待定名单、跟进模板 | 20 户排期表、日历邀请 | Day3 半天 |
| 5 | 访谈/录音 | **必须本人** | 访谈员手册、13 列模板 | 录音/笔记、13 列记录 | Day4–Day7，每天 ≤6 户 |
| 5b | 转写 | 机器（可选） | 音频目录 | `var/g1/transcripts/*.txt` | 夜间批处理 |
| 6 | 分析 | 脚本 + 本人复核 | `var/g1/interviews.csv` | `var/g1/g1_report.md` | 30 分钟 |
| 7 | 决策 | **必须本人** | 分析报告、补访名单 | `var/g1/decision.md` | 1 小时 |

### 1.3 只有这 4 件事不能外包

1. **发帖**：必须用你本人的账号发，且进群先经群主同意；代发/小号会被判广告，也会让"不推销"的承诺失效。
2. **约访排期**：配额、城市上限、组别缺口只有你能拍板；脚本只会给"合格/待定"，不会替你决定"这户要不要换"。
3. **访谈与录音同意**：同意必须由受访者**本人**给出，访谈员不能代答、不能默示同意；孩子在场必须停录。
4. **决策签字**：G1 过不过、要不要补访、是否转 B2B，必须你签字；脚本只出数，不出结论。

其余环节可以自动化，但**不能不看**：导出要核行数、筛选要核配额、分析要核逐户场景判定。

### 1.4 Day1–Day7 与 7 步的对应

| 天 | 走到第几步 | 当天必须完成的检查点 |
|---|---|---|
| Day1 | 准备（第 1 步前置） | 表单可提交、三版文案定稿、排期表建好 |
| Day2 | 1 → 2 | 报名入口可访问；当天至少导出一次，确认列名可识别 |
| Day3 | 2 → 3 → 4 | `summary.json` 的合格/待定/不合格三数相加等于报名数；20 户排期落位 |
| Day4–Day7 | 5 → 5b → 6 | 每天 ≤6 户；当天 15 分钟内填完 13 列；转写只做夜间批处理 |
| Day7 21:00 | 6 → 7 | 报告 + 补访名单 + 决策 memo 三件齐 |

## 2. 逐步命令

> 每步固定六项：**目的 / 命令 / 输入 / 产物 / 检查点 / 失败处理**。命令先跑 `--dry-run` 或 `--help`，确认后再正式执行。

### 2.1 发帖

**目的**：用三版文案拿到 ≥30 份报名（目标，实际以表单提交计），且不产生"推销/承诺"的误解。

**命令**（人工动作，无脚本）

```text
文案位置：docs/招募帖与问卷-v0.1.md §1
  版 1（论坛/HA 群）→ 版 1 全文 + 置顶评论三条
  版 2（B 站/小红书）→ 版 2 全文 + 置顶评论四条
  版 3（适老化/社区群）→ 版 3 全文 + 群内置顶四条
发布账号：你本人的账号（论坛 ID / B 站 / 小红书 / 微信群）
报名入口：【填：表单链接】（三个渠道同一个链接，可加 ?src=forum / ?src=video / ?src=group 便于分辨来源）
```

**输入**：三版文案、表单链接、渠道清单（见招募文档 §3）。

**产物**：投放记录（渠道/帖子链接/发布时间/曝光或群人数/报名数），当天 21:00 更新一次。

**检查点**

- [ ] 三版正文都**不含**价格、不含"内测/免费试用/名额有限"。
- [ ] 置顶评论都写了"红包访谈结束即发、与买不买无关"。
- [ ] 链接在自己手机上打开能提交，提交后能看到感谢页。
- [ ] 表单关闭"收集微信昵称/头像"；Q12 是"录音意愿 + 联系方式"两个字段。
- [ ] 进群发帖已获群主同意；同一文案跨群只微调称呼，不刷屏。

**失败处理**

| 症状 | 处理 |
|---|---|
| 链接打不开 / 被平台拦截 | 换备用表单服务；先在 1 个群小范围试投，确认可提交再全渠道 |
| 帖子被判广告/删除 | 按平台规则申诉；改发"经验分享"角度，不重复贴同一段；**不加价格、不加紧迫感** |
| 群主拒绝 | 换备选渠道（招募文档 §3 的备选列）；不私聊群成员逐个拉人 |
| 报名远低于 30 | 按 §5 硬规则：Day3 只筛不补、Day4 照常开访，缺口顺延一周补招，**不降 H1–H4** |

### 2.2 导出报名

**目的**：把表单后台数据变成脚本能读的 UTF-8 CSV，且列名能被识别。

**命令**

```text
腾讯问卷：数据/统计 → 导出 → 选择 CSV → 下载
问卷星：分析 & 下载 → 下载答卷 → CSV → 下载
保存为：var/g1/responses.csv（UTF-8；Excel 另存请选「CSV UTF-8」）
```

列名不一致时，先跑 dry-run 看脚本认不认，再决定是否加映射：

```bash
# 1) 先看脚本能不能自动识别（不写文件）
.venv/Scripts/python.exe scripts/g1_screen.py --input var/g1/responses.csv --dry-run --limit 5

# 2) 认不出时，写 var/g1/mapping.json，再带上 --mapping
.venv/Scripts/python.exe scripts/g1_screen.py --input var/g1/responses.csv --dry-run --mapping var/g1/mapping.json
```

`var/g1/mapping.json` 示例（键为 `Q1..Q12` / `contact` / `exclude`，值为导出 CSV 的**实际列名**）：

```json
{
  "Q1": "1、常住城市级别",
  "Q2": "2、使用 Home Assistant 多久",
  "Q3": "3、HA 安装形态",
  "Q4": "4、已接入且可控的实体数",
  "Q5": "5、哪些设备已接入 HA",
  "Q6": "6、同住成员",
  "Q9": "9、近 3 个月发生过的异常",
  "Q10": "10、怕出事的程度",
  "Q12": "12-1、录音意愿",
  "contact": "12-2、联系方式",
  "exclude": "人工核对排除项"
}
```

> 说明：`Q12` 只映射"录音意愿"那一列；`contact` 单独映射联系方式。若导出列名里没有"联系方式/微信/手机"字样，**必须**显式写 `"contact": "实际列名"`，否则脚本找不到联系方式列（不影响筛选判定，但后续约访会缺联系方式）。

**输入**：表单导出 CSV（可能带 BOM、可能列名带题号前缀）。

**产物**：`var/g1/responses.csv`（+ 可选 `var/g1/mapping.json`）。

**检查点**

- [ ] 行数 = 表单提交数（去掉测试提交）。
- [ ] 表头能被 `--dry-run` 识别：不报"缺列"或大量"缺失/无法识别"。
- [ ] 多选列在**一个单元格**内（用 `;` `|` `、` 等分隔均可），没有被拆成多列 0/1。
- [ ] Q12 是两列（录音意愿 / 联系方式），不是一列拼在一起。
- [ ] 文件编码 UTF-8；中文不乱码。

**失败处理**

| 症状 | 处理 |
|---|---|
| 中文乱码 | 用 Excel「另存为 → CSV UTF-8（带 BOM）」；脚本按 `utf-8-sig` 读取，带 BOM 可正常读 |
| 列名全不认识 | 用上面的 `--mapping`；先用 `--limit 5` 小样本验证，不要一次跑全量 |
| 多选被拆成多列 | 优先改导出设置"合并多选"；不能改则在 Excel 合并成一列再导出（不要手工改判定值） |
| Q12 两列之一缺失 | 在 `--mapping` 里补 `Q12` 或 `contact`；两列都缺则回表单补采 |
| `--mapping` 报"指向的列不存在" | 核对表头 **逐字**（含空格、全角括号）；报错信息会打印实际表头，照抄修正 |

### 2.3 筛选

**目的**：把报名分成合格 / 待定（备选池）/ 不合格，并按 8/6/6 配额与 6/7/7 三档排出顺序。

**命令**

```bash
# 1) 只看摘要，不写文件
.venv/Scripts/python.exe scripts/g1_screen.py --input var/g1/responses.csv --dry-run

# 2) 正式输出到 var/g1/
.venv/Scripts/python.exe scripts/g1_screen.py --input var/g1/responses.csv

# 3) 可选：严格按 §1.1 字面 H3 复算一遍，输出到独立目录，两份都留档
.venv/Scripts/python.exe scripts/g1_screen.py --input var/g1/responses.csv \
  --out-dir var/g1/strict --strict-h3
```

**输入**：`var/g1/responses.csv`（± `--mapping`）。

**产物**：`var/g1/screened.csv`（原列 + `verdict/group/quota_slot/plan/reason`）、`var/g1/summary.json`。

**看 `summary.json` 的哪些字段**

| 字段 | 看什么 | 正常值（满分时） |
|---|---|---|
| `total` / `qualified` / `pending` / `rejected` | 三数相加必须等于 `total` | 30 份报名 → 合格 20 左右 |
| `by_group` | 组别配额 | 老人 8 / 儿童 6 / 纯危险设备 6 |
| `group_quota` | 配额上限（只读，不改） | 8 / 6 / 6 |
| `by_plan` / `plan_target` | 三档分流 | 合格 20 户时 6 / 7 / 7 |
| `first_tier_count` / `first_tier_limit` | 一线/新一线合格数 | ≤12 |
| `pending_by_reason` | 待定原因（组满/城市超限/设备不足） | 用于补位排序 |
| `rejected_by_reason` | 不合格原因（排除项/H1–H4） | 用于核对是否误杀 |
| `bonus_checks` | 老人组独处 ≥4、误断/误开 ≥3；儿童组 ≤6 岁 ≥3、Q8 代理 ≥2 | `ok: true` 越多越好 |

> **重要**：`by_plan` 只有在合格户正好 20 时才显示 6/7/7；不足 20 时脚本按最大余数法按比例分配，这是预期行为，**不是 bug**。不要为了凑 6/7/7 把待定户转合格。

**`--strict-h3` 什么时候用**

- **日常排期不要加**。默认口径把"Q6 仅成年人 + 已接入危险设备"作为纯危险设备组的 H3 等价来源，否则 §1.3 的"纯危险设备组 6 户"永远招不到。
- **只在两种时候加**：① 需要按 §1.1 字面口径复算一遍做敏感性检查（输出到 `var/g1/strict`，两份并列留档）；② 外部有人质疑"你们是不是放宽了 H3"，用这份结果解释差异。
- 加了以后纯危险设备组会因 H3 未过被判不合格，这是**预期差异**，不是脚本错误；两份结果都要留，不得只留对自己有利的那份。

**检查点**

- [ ] 合格 + 待定 + 不合格 = 报名总数。
- [ ] `by_group` 不超过 8/6/6；一线/新一线 ≤12；超出部分应在 `pending`（原因 `first_tier`），不是被硬塞进合格。
- [ ] 待定原因分布合理；若"组满"很多，说明该组已够 6/8 户，停止该渠道投放。
- [ ] 抽查 3 行 `screened.csv`：`verdict/reason` 与原始答案能对上。
- [ ] `bonus_checks` 的 `note` 看一遍：儿童组"碰过危险开关/说过危险指令"是 Q8 代理，**需访谈确认**。

**失败处理**

| 症状 | 处理 |
|---|---|
| 大量 `H3 未过` | 先确认不是 `--strict-h3`；再看 Q6 列是否被识别（两列同名/合并） |
| 合格数远小于预期 | 看 `rejected_by_reason`；常见是 Q4 被识别成"0–9"或 Q5 分隔符没拆开 |
| 一线/新一线超 12 | 超出户进待定池，不手工改城市；补招优先二三线 |
| 待定户想直接转合格 | **禁止**；只能等有人退出按序补位（招募文档 §5 硬规则 2） |

### 2.4 约访

**目的**：把合格户排进 7 天日程，20 户全部有户号、组别、档位、时间，且每天 ≤6 户。

**命令**（人工动作 + 模板）

```text
话术位置：docs/G1跟进消息模板-v0.1.md
  第 1 条 报名确认 → 收到表单 2 小时内
  第 3 条 改约     → 对方提出改期时
  第 4 条 前 24h   → 访谈前一天同一时刻
日历：每户占 50 分钟（0–5′ 行政 + 45′ 六段），两户之间留 30 分钟填表
排期上限：同一天 ≤6 户；老人组上门场只到小区门口
```

排期表模板（复制到表格工具，一行一户）：

| 户号 | 组别 | 档位 | 渠道 | 城市级别 | 访谈日期 | 时段 | 线上/上门 | 录音意愿 | 状态 | 备注 |
|---|---|---|---|---|---|---|---|---|---|---|
| P01 | 老人 | A | 版 3 | 新一线 | Day4 | 20:00 | 线上 | 接受录音 | 已约 | — |

**输入**：`screened.csv` 的合格行、联系方式、跟进模板。

**产物**：20 户排期表 + 日历邀请（含链接/地址只到小区）。

**检查点**

- [ ] 20 户都有户号（P01–P20）、组别、档位；档位按 `screened.csv` 的 `plan` 列，**不现场改**。
- [ ] 一线/新一线 ≤12；老人 8 / 儿童 6 / 纯设备 6（不足时如实记录缺口，不凑数）。
- [ ] 每天 ≤6 户；两户间 ≥30 分钟。
- [ ] 老人组 ≥4 户独处 ≥4h、≥3 户误断总电/误开门锁；儿童组 ≥3 户 ≤6 岁、≥2 户会自己用语音（以 `bonus_checks` 为初判，访谈确认）。
- [ ] 每户已发"前 24h 确认"，且短信里没有价格、没有链接。

**失败处理**

| 症状 | 处理 |
|---|---|
| 改约 | 用模板第 3 条，只要两个时段；改约不影响红包 |
| 连续两次改约 | 进待定池，从备选池按序补位；不无限等待 |
| 当天缺席 | 24 小时内补约一次；仍不就换人，不把缺席户计入完成 |
| 某组缺口（如老人组只有 6 户） | 顺延一周补招；**不把纯设备户改标成老人户** |

### 2.5 访谈与录音

**目的**：每户拿到可填 13 列的具体事件，且录音/笔记符合单独同意。

**命令**（人工动作）

```text
入口：docs/G1访谈员手册-v0.1.md
  §0 速查卡（打印一页）
  §2.1 开场白 → §2.2 录音单独同意（PIPL 五要素）→ §2.3 红包说明
  §3 六段操作卡（B/K/A/C/M/N 编号）
  §5 异常处理（老人方言/儿童/情绪/拒绝录音/中途退出/亲友从业者）
文件命名：var/g1/audio/P01_YYYYMMDD.m4a（不写姓名、不写小区）
```

**输入**：访谈员手册、13 列记录模板、演示环境（30 秒）。

**产物**：每户录音（或"仅笔记"标记）+ `var/g1/interviews.csv` 一行 13 列。

**只接受笔记的户怎么记**

- 全程**不录音、不补录、不让记录员代录**；开场明确"那我只做笔记"。
- "关键原话"现场手记，照原样抄，备注列写 `仅笔记；关键原话=现场手记`。
- 录音文件目录里**不应有该户音频**；验收时以"音频文件缺失 + 备注=仅笔记"为正确状态，不是漏录。
- 红包、时长、后续联系完全不变。

**检查点**

- [ ] 每户备注列有 `录音=同意（HH:MM）/ 仅笔记 / 中途停止（HH:MM）` 三态之一。
- [ ] 儿童进入画面时录音已暂停；音频里没有孩子声音。
- [ ] 每户访谈后 15 分钟内填完 13 列；"关键场景"含时间锚。
- [ ] 当天 ≤6 户；超出会直接导致记录失真。

**失败处理**：全部按访谈员手册 §5 执行（拒绝录音→只做笔记；中途退出→按是否走完关键事件段决定计不计完成；识别亲友/从业者→终止、不发红包、不计 20 户）。本手册不另立规则。

### 2.6 转写

**目的**：把录音变成可检索的文本，辅助填 13 列；**转写不是 G1 的必要条件**，没有它也能完成。

### 2.7 分析

**目的**：把 13 列记录变成 G1 报告，给出三条判据的实际值、NPS、补访名单。

**命令**

```bash
# 1) 先 dry-run 看摘要，不写报告
.venv/Scripts/python.exe scripts/g1_analyze.py --input var/g1/interviews.csv --dry-run

# 2) 正式输出 var/g1/g1_report.md
.venv/Scripts/python.exe scripts/g1_analyze.py --input var/g1/interviews.csv

# 3) 一键版（筛选 + 分析 + dashboard.html；真实数据不要加 --demo）
.venv/Scripts/python.exe scripts/g1_pipeline.py \
  --responses var/g1/responses.csv \
  --interviews var/g1/interviews.csv \
  --out-dir var/g1
```

**输入**：`var/g1/interviews.csv`（13 列，P01–P20，**不含模板示例行**）。

**产物**：`var/g1/g1_report.md`（+ 一键版会额外产出 `dashboard.html`）。

**看 `g1_report.md` 的五处**

| 位置 | 看什么 | 判读规则 |
|---|---|---|
| 一、样本概览 | `登记户数 / 有效户数 / 目标户数 / 有具体关键场景户数 / 痛点 ≥4 户数` | 有效户数必须等于实际访谈户数；不足 20 时报告会标"阶段性结论" |
| 二、场景关键词归类 | 门锁/燃气/总电/大功率/撤防/误触/儿童/老人 的命中户数 | 多标签，占比之和 ≠100%；"其他"多说明记录写得抽象 |
| 三、痛点分布 | 5–1 各档户数、均值 | 痛点 ≥4 是判据②，口径见验证包 §2.7 |
| 四、NPS | 推荐者/被动者/贬损者/NPS 值 | 缺失回答不进分母；NPS 为 `-` 表示无有效回答 |
| 五、G1 判据 | ① 关键场景 `x/20`；② 痛点 ≥4 `y/20`；③ 显示"未采集"；有效户数 | ①目标 ≥12/20；②目标 ≥8/20；③**必须人工判读**，见下 |
| 七、未达标项与补访 | 未达标项 + 建议补访名单（户号/问题/动作） | 补访名单是下一步行动清单，不是"建议看看" |

**判据③必须人工处理（脚本不采集、不推断）**

13 列模板里没有"是否愿意承担费用"这一列，因此报告第③行固定显示"未采集 / 未计入"。**不要把"未采集"读成"通过"**。人工做法：

1. 逐户看"关键原话"和"备注"，只认**明确表达**（如"这个我会买/愿意按年给"），模糊表态（"挺好的""可以考虑"）不算。
2. 在 `var/g1/decision.md` 里写清"判据③：明确 X/20 户，依据为 P0x 原话摘录"，并附 3 条原话。
3. 判据③未达 6/20 → G1 不通过，不得用"方向是好的"替代。

**`--target-households` 与 `--scenario-threshold`**

- 默认 20 / 12，**不要为了让结果好看去改**。
- 只有一种合法情况改 `--target-households`：实际只招到 N<20 户、且已决定"如实按 N 户收口"。此时报告与 memo 都必须写"分母改为 N，不可与 20 户口径混比"。
- `--scenario-threshold` 属于事前约定的判据线，**事后修改即作弊**；确需改，必须在 memo 记录"改前/改后 + 理由 + 谁批准"。

**检查点**

- [ ] 有效户数 = 实际完成访谈户数（不是排期户数，也不是报名数）。
- [ ] 逐户场景判定抽查 5 户：`scenario_ok=是` 的"关键场景"确实含时间锚，不是"他很担心"。
- [ ] 判据①②有明确通过/未通过；不足 20 户时报告有"阶段性结论"字样。
- [ ] 补访名单每户都有"问题 + 建议动作"。
- [ ] 报告里的数字与 `screened.csv`（户数/组别）能对上，对不上先查记录表。

**失败处理**

| 症状 | 处理 |
|---|---|
| `有效户数` 比实际多 1 | 模板里的 `P01` 示例行没删（见 §4.2） |
| 大量"痛点未填/无法解析" | 记录表痛点列写了"挺高""4 分"之类；回填为 1–5 整数 |
| 大量"场景不成立" | 关键场景写成态度而非事件；补访并回填时间锚 + 谁 + 设备做了什么 |
| 报告说 NPS 为 `-` | NPS 列空或写了"大概 8"；回填 0–10 整数或 `NA` |
| 一键版 `dashboard` 报错 | 以 `screened.csv/summary.json/g1_report.md` 为准，看板只是浏览层；修复前不阻塞决策 |

### 2.8 决策

**目的**：按事前约定的判据给出"过 / 不过 / 补访后再判"，并当天落行动。

**判据（只列三项，整表见验证包 §7，不重复）**

1. **① 具体事件**：≥12/20 户能讲出近 3 个月的具体误操作或"不敢用"事件。
2. **② 痛点强度**：≥8/20 户痛点 ≥4。
3. **③ 费用意愿（口头，仅方向）**：≥6/20 户明确愿意为"确认 + 审计"承担费用；脚本不采集，人工判读并留原话。

**通过 → 下一步（不隔夜）**

- 记录三档的实际值与证据强度，进入 G2 排期。
- 价格链接在访谈后 24 小时由统一流程发；**访谈员不在现场发、不在当天发**。
- 每户固定一档（A/B/C），禁止切换比价。

**不通过 → 当天就做**

- 任一判据不过 → 命题不成立，**当天启动转 B2B 动作**（目标客户、报价模型、各谈 3 家、拿到 1 份书面意向），不是"再考虑一周"。
- 若只是样本不足（<20 户），**不算通过也不算不通过**：写"样本未满，补访后重判"，补访名单当天发出。
- 判据③无记录 → 视为未通过，不得用"大家反应挺好"替代。

**命令**（写 memo，人工）

```text
文件：var/g1/decision.md（建议路径，不入 docs，避免与内部文档混放）
```

**决策 memo 骨架（7 行，复制填写）**

```markdown
# G1 决策 memo · YYYY-MM-DD
- 结论：通过 / 不通过 / 样本未满待补访
- 判据①：__/20（目标 ≥12）；依据：报告第五节
- 判据②：__/20（目标 ≥8）；依据：报告第三节
- 判据③：__/20（目标 ≥6，人工判读）；依据原话：P__、P__、P__
- 证据强度与限制：有效户 __/20；未看演示 __ 户；仅笔记 __ 户；方言/代答 __ 户
- 补访计划：__ 户，截止 YYYY-MM-DD，负责人 ____
- 下一步：进入 G2 / 转 B2B；负责人 ____；日期 YYYY-MM-DD
```

**检查点**

- [ ] memo 的三个数字与 `g1_report.md` 一致（判据③除外，它是人工值，需附原话）。
- [ ] 有明确结论，没有"基本通过""差不多"。
- [ ] 有负责人和日期；不通过时有当天的 B2B 动作清单。
- [ ] memo 里没有引用 demo 数字。

## 4. 常见错误 8 条

| # | 症状 | 原因 | 处理 |
|---|---|---|---|
| 4.1 | 脚本报"缺列"或大量"缺失/无法识别" | 导出列名与模板不一致（带题号前缀、括号全半角不同、多选被拆列） | 先 `--dry-run --limit 5`；用 `--mapping` 显式映射；报错会打印实际表头，逐字核对 |
| 4.2 | 报告"有效户数"比实际多 1（如 20 户变 21） | 直接复制了 `docs/访谈记录模板.csv`，第 2 行 `P01` 示例没删 | 打开 `interviews.csv` 删掉示例行（P01 示例那行内容为"老人/杭州/Docker/24"等），只保留真实户；删后重跑 |
| 4.3 | Q5/Q6 只识别出 1 个选项，H2/H3 判错 | 多选分隔符不统一：导出用分号、顿号、竖线或换行，或每选项一列 0/1 | 脚本支持分号、竖线、逗号、中文标点与换行；若被拆成多列，改导出设置"合并多选"或 Excel 合并后再导出，**不要手改判定值** |
| 4.4 | 合格户里一线/新一线超过 12 | 脚本按报名顺序先到先得，超出会转 `待定（first_tier）`；有人手工把待定改合格 | 不改城市值、不改 verdict；让超出户留在备选池，补招优先二三线；`summary.json` 的 `first_tier_count` 必须 ≤12 |
| 4.5 | 纯危险设备组 1 户都筛不出来 | 误加了 `--strict-h3`，H3 只认老人/儿童 | 日常去掉 `--strict-h3`；严格口径只用于敏感性复算，输出到 `var/g1/strict` 并两份留档 |
| 4.6 | 分析里有录音、但该户 Q12 选的是"只接受笔记" | 访谈员违规录音，或把"随便/都行"当成同意 | 立即停止并删除该户音频；记录事件；该户按"仅笔记"重记；严重违规按手册 §5.4 处理，**不补录、不事后补同意** |
| 4.7 | 只有 18 户，却按 20 户算比例说"90% 通过" | 把有效户数当分母，或忽略报告的"阶段性结论" | 分母固定 20；不足 20 写"样本未满，补访后重判"，不得判 G1 通过；补访名单当天发出 |
| 4.8 | 把 `var/g1/demo/out/` 的"合格 20、判据通过"写进汇报 | 没注意页首/字段的 `SYNTHETIC DEMO` 标注 | 引用前先看 `summary.json.synthetic_demo` 是否为 `true`；为 `true` 一律不引用；demo 只用于检查格式 |

## 5. 验收清单：G1 结束当天必须有的 6 件东西

| # | 东西 | 位置 | 验收标准（逐条打勾） | 缺了会怎样 |

| 6 | **决策 memo** | `var/g1/decision.md` | 结论明确（通过/不通过/待补访）；三条判据实际值 + 判据③原话；证据强度与限制；负责人 + 日期 | 没有签字就没有决策，团队会继续"再看看" |

**当天最后 10 分钟的三个自检**

1. 六件东西是否都能在 1 分钟内找到？（找不到 = 没交付）
2. 报告里的数字是否与名单、记录表对得上？（对不上先查 4.2/4.3）
3. memo 里有没有出现 demo 数字或"基本通过"？（有就删掉重写）
