# 家庭语音安全层 — 5 分钟演示脚本 v0.1

> **一句话边界（先说，且必须说）**：这是 **simulated（模拟）后端** 的确定性演示，**不是 Home Assistant 真机证据**。
> 本演示不接真实 HA、不联网、不启用 ASR/TTS；屏幕上的「灯」「门锁」都是 `devices/devices.json` 里的模拟实体，不控制任何真实负载。
> 真机证据的唯一口径见 `docs/HA真机冒烟结果-v0.1.md`（当前状态：**冒烟未执行 / blocked**），本文不替代它。

- 演示命令：`python scripts/demo_showcase.py`（参数以 `python scripts/demo_showcase.py --help` 为准）
- 演示代码：`scripts/demo_showcase.py`（复用 `hvsl.app.build_engine` + `SimulatedBackend`，不复制决策逻辑）
- 自动化校验：`python -m pytest -q tests/test_demo_showcase.py`（15 个用例）
- 总时长：约 5 分钟（台词按 0:00–5:00 排）

---

## 1. 这 5 分钟要讲清的业务问题

| 业务问题 | 演示里的技术解法 | 观众能看到的收益 |
| --- | --- | --- |
| 家人一句「开大门」，语音助手听错就执行，风险不可逆 | 风险分级（low / confirm / deny）+ 确认门禁：危险计划只挂起，0 下发 | 第 2 步「注意看：它现在不会开门」 |
| 每次开灯都要二次确认，用户会关掉语音助手 | 低风险直执行，不打扰 | 第 1 步直接 executed，1 次下发 |
| 用户确认后系统重试/重放，门被开两次 | 幂等键 + 单次确认令牌，重复确认拒绝且不再下发 | 第 3、4 步：0 → 1 → 仍为 0 增量 |
| 出了事说不清「谁在什么时候让哪个设备做了什么」 | 审计表（原句/风险/确认状态/下发状态）+ CSV/JSON 导出 | 第 5 步 3 条关键决策可核对 |

一句话总结（收尾时说）：**低风险不打扰、危险动作不失控、每一次决定都可追溯。**

## 2. 5 步预期结果（核对表）

| 步骤 | 用户/动作 | 预期 `Decision.kind` | `dispatch_count` | 关键结果 |
| --- | --- | --- | --- | --- |
| 1 | 说「开客厅大灯」 | `executed` | `1` | `hvs.light.turn_on -> light.living_room_main` |
| 2 | 说「开大门」 | `awaiting_confirmation` | `0` | 返回令牌但**不打印**；`spoken_message` 不含令牌 |
| 3 | 用第 2 步令牌 `confirm` | `executed` | `1` | `hvs.lock.unlock -> lock.front_door` |
| 4 | 同一令牌再 `confirm` | `rejected`（也接受 `deduplicated`） | `0` | 后端累计下发仍为 2 次 |
| 5 | 导出 `audit.csv` / `audit.json` | `audit_export` | 记录 9 行 | 关键决策 3 条；令牌不落盘 |

> 行数 `9` 是当前引擎版本的实测值（每步的 utterance/nlu/confirm/dispatch/result 行合计）；**关键决策固定为 3 条**（2 条已执行下发 + 1 条待确认挂起），行数随版本可能变化，以 stdout 为准。

## 3. 逐句台词（0:00–5:00）

### 0:00–0:30 开场（先立边界）

> 「今天用 5 分钟演示家庭语音安全层。先说清楚：**这是模拟后端演示，不是 HA 真机证据**。屏幕上的灯和门锁都是清单里的模拟实体，不接真实设备，也不联网。」

> 「我们要解决的不是『能不能听懂』，而是『听懂之后敢不敢直接做』。所以这条链只做四件事：分级、挂起、幂等、留痕。」

打开终端，先跑一次 dry-run（10 秒）：

```bash
python scripts/demo_showcase.py --dry-run
```

> 「这是今天的 5 步路线图。dry-run 不建引擎、不写数据库，只是让您先看我们要验证什么。」

### 0:30–1:30 第 1 步：低风险直执行

运行：

```bash
python scripts/demo_showcase.py --audit-dir demo_out
```

> 「第一句，普通开灯。**普通开灯不应该打断用户**——看屏幕：」

```text
[1/5] 低风险直执行
  用户说：开客厅大灯
  决策：executed
  下发次数：1
  系统回复（TTS 文本）：已执行 hvs.light.turn_on -> 客厅大灯
  关键结果：hvs.light.turn_on -> light.living_room_main：executed（已下发）
```

> 「`executed`、`dispatch_count=1`。它没有问『您确定吗』，因为开一盏灯的风险等级是 low。**低风险直执行，是为了让用户愿意继续用。**」

### 1:30–2:30 第 2 步：危险动作挂起（本场核心）

> 「第二句，开大门。**注意看：它现在不会开门。**」

```text
[2/5] 危险动作挂起
  用户说：开大门
  决策：awaiting_confirmation
  下发次数：0
  系统回复（TTS 文本）：【入户门锁】属于危险操作，需要你确认。120 秒内未确认将自动作废，确认前不会下发任何指令。
```

> 「`awaiting_confirmation`、`dispatch_count=0`。策略把它判成 `door_unlock`，计划被停在确认门禁里，**一个字节都没有发给门锁**。」

> 「再看这句话本身：**里面没有确认令牌**。令牌只通过程序接口交给调用方，不进 TTS、不进通知、不进日志。屏幕上您看不到它，这是设计，不是显示问题。」

### 2:30–3:20 第 3 步：确认后执行

> 「现在我才说『确认』。脚本用第 2 步的令牌调用 `confirm`：」

```text
[3/5] 确认后执行
  用户说：确认（confirm）
  决策：executed
  下发次数：1
  系统回复（TTS 文本）：（已确认）已执行 hvs.lock.unlock -> 入户门锁
  关键结果：hvs.lock.unlock -> lock.front_door：executed（已下发）
```

> 「下发次数从 0 变成 1。**危险动作不是不能做，而是必须由人明确放行一次。**」

### 3:20–4:00 第 4 步：重复不重发

> 「最后做一个坏事：同一张确认票，再确认一次。**它必须拒绝，绝不能再开一次门。**」

```text
[4/5] 重复不重发
  用户说：确认（重复，同一令牌）
  决策：rejected
  下发次数：0
  系统回复（TTS 文本）：确认无效：令牌不存在、已过期或已被使用
```

> 「`rejected`、`dispatch_count=0`，后端累计下发仍然是 2 次（灯 1 次 + 门 1 次）。确认令牌是单次的；重试、重放、网络抖动都不会变成第二次开门。」

### 4:00–5:00 第 5 步：审计可导出 + 收尾

> 「最后看审计。谁在什么时候要做什么、风险等级、有没有确认、有没有下发，都能导出：」

```text
[5/5] 审计可导出
  记录条数：9
  关键决策：3 条（2 条已执行下发 + 1 条待确认挂起）
  CSV 路径：demo_out\audit.csv
  JSON 路径：demo_out\audit.json
```

> 「3 条关键决策：开灯已执行、开门已挂起、开门确认后已执行。原句默认脱敏成 `[redacted]`，令牌从不落盘。」

> 「收尾三句话：低风险不打扰；危险动作不失控；每一次决定都能追溯。**再强调一次：这是模拟后端的行为演示，真机是否成立要看 HA 真机冒烟结果，当前那份结果是 blocked，不能拿今天这段当真实设备证据。**」

## 5. 常见问题（现场被问到时照着答）

### Q1：灯没开 / 第 1 步不是 `executed`

- 本演示的「灯」是 `SimulatedBackend` 里的内存状态，**没有真实灯**，不要回答「灯坏了」。
- 先看 `[1/5]` 的 `决策` 行：若为 `clarification_required`，说明指令在当前设备清单里能匹配到多个设备（见 §7 口径差异）。演示脚本固定用「开客厅大灯」，正常应为 `executed`。
- 若出现 `[FAIL]`，先跑 `python scripts/demo_showcase.py --dry-run` 核对计划，再跑 `python -m pytest -q tests/test_demo_showcase.py`。**不要现场改 `hvsl/` 生产代码。**

### Q2：门锁没确认 / 第 2 步没有令牌给人看

- `awaiting_confirmation` 就是预期结果，**它本来就不该下发**。
- 令牌被故意排除在 stdout、JSON、审计之外；需要它的是程序调用方，不是观众。想验证确认流程，让脚本自己跑完第 3 步即可。
- 确认窗口默认 120 秒（`Settings.confirm_ttl_seconds`）；手动复现时如果超时，会得到 `rejected`，这是过期保护，不是故障。

### Q3：重复确认被拒，是不是 bug？

- 不是。确认令牌是**单次**的：`confirm` 成功后令牌立即作废，第二次确认返回 `rejected` 或 `deduplicated`，且 `dispatch_count=0`。
- 这正是第 4 步要证明的「重试/重放不会变成第二次开门」。测试同时接受 `rejected` 与 `deduplicated` 两种实现结果。

### Q4：TTS 不可用 / 为什么没有声音？

- 本演示**不启用 ASR/TTS**，也不联网；屏幕上的「系统回复（TTS 文本）」只是准备给 TTS/通知的文本，不是播放出来的语音。
- 不要在演示中承诺「语音链路已跑通」。语音链路的真机/本地模型情况另见项目其他文档；本脚本只证明决策层。

### Q5：审计路径在哪 / 演示结束文件怎么没了？

- 默认写临时目录，随进程退出删除（避免污染仓库 `var/`）。
- 要保留：`python scripts/demo_showcase.py --audit-dir demo_out`，会得到 `demo_out/audit.csv` 与 `demo_out/audit.json`。
- CSV 表头固定（`AUDIT_CSV_COLUMNS`：`trace_id,seq,session_id,ts,stage,...`），可用于表格核对；`utterance` 默认脱敏。

### Q6：为什么第 5 步是 9 行，不是 3 行？

- 3 是**关键决策**数（2 条已执行下发 + 1 条待确认挂起）；9 是完整审计行数，包含每步的 `utterance` / `nlu` / `confirm` / `dispatch` / `result` 留痕。
- 版本升级后总行数可能变化，**关键决策数应保持 3**；以脚本实际 stdout 与测试为准。

## 6. 不能说的话（红线）

1. **不能说「已经在 HA 真机验证过」**。没有。真机冒烟见 `docs/HA真机冒烟结果-v0.1.md`，状态是 **blocked / 未执行**。
2. **不能说「接了真实门锁 / 真实灯 / 真实燃气阀」**。全部是 simulated 实体，不接真实负载。
3. **不能说「100% 安全」「绝不会误操作」「绝对不会被绕过」**。演示只证明这条链在给定输入下的行为，不证明绝对安全。
4. **不能说「已上线 / 已量产 / 已收费」**。演示不构成商业交付证据。
5. **不能把模拟结果当真实设备证据**，也不能把 `SimulatedBackend` 的状态截屏当成家庭现场。
6. **不能承诺确认率、误报率、延迟等指标**。本演示不产出指标；指标口径见 G3 内测手册与事件字典。
7. **不要展示或索要确认令牌**。令牌是单次凭证，泄露即等于把「开门权」交出去。
8. **不能说「重复确认失败是系统故障」**。那是幂等与单次令牌的预期行为。
